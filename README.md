# 投資組合分析 · Portfolio Analytics

[![CI](https://github.com/seanhong1215/investment-portfolio/actions/workflows/ci.yml/badge.svg)](https://github.com/seanhong1215/investment-portfolio/actions/workflows/ci.yml)

損益與資產分佈，並以價值投資指標評估個股體質與合理買進區間。

> React 19 · TypeScript · Vite · Zustand · Tailwind 4 · Vitest
> 純前端（本地優先，可選 Firebase 雲端同步）· 深淺色雙主題

**<https://investment-portfolio-liard.vercel.app/>**

| 欄位 | 值 |
|---|---|
| 股票代碼 | `DEMO` |
| ROE (%) | `32` |
| 淨利率 (%) | `24` |
| 負債股權比 (倍) | `0.6` |
| 本益比 P/E (倍) | `19` |
| 季度盈餘年增率 (%) | `14` |
| 流動比率 (倍) | **刻意留空** |

留空的欄位是觀察重點，畫面會呈現三件事：

- 表單即時顯示「已填權重 **90** / 需 60 才能評級」。權重表與計分規則來自同一份來源。
- 流動比率的卡片為**虛線邊框加問號圖示**，標示「本項 10 分權重已排除於評分之外
  （未計零分）」，而非以叉號呈現為不及格。
- 分數標註「在 **90** 分可評權重上正規化」，並列出「未納入評分：流動比率」。

將流動比率填入 `1.6` 後重新分析，分數由 79 降為 76，因為該項指標確實不理想。
**「無資料」與「數值不佳」是兩種不同的狀態**，此區別正是重構前被
`parseFloat(v || '0') || 0` 抹除的部分。

> 示範數值僅供操作演示，不代表任何真實標的，亦不構成投資建議。

## 設計重點

本專案的目標不在功能數量，而在於呈現取捨與工程判斷。以下五項依重要性排序，
第一項為整份程式碼的核心主張。

### 1. 在財務系統中，「沒有資料」不等於 0

巴菲特評分包含六項指標，權重加總為 100。Alpha Vantage 的免費 `OVERVIEW` 端點
**不回傳** `DebtToEquityRatio` 與 `CurrentRatio` 兩個欄位，而重構前的 adapter 寫法為：

```ts
const parse = (v: string | undefined) => parseFloat(v || '0') || 0
```

結果是每一檔股票都落入以下狀態：

| 指標 | 缺漏後的值 | 評分函數 | 結果 |
|---|---|---|---|
| 負債股權比（15 分） | `0` | `reverseScale(0, 0.3, 1.5)` = 1 | **恆為滿分** |
| 流動比率（10 分） | `0` | `linearScale(0, 0.8, 2.5)` = 0 | **恆為零分** |

100 分中有 25 分與公司體質無關，且分數上限被壓低至 90（A 級門檻為 80）。
沒有任何測試會失敗，畫面亦無異常，屬於最不易察覺的一類缺陷。

評分函數本身已具備 `value === null` 的處理路徑，資訊是在 adapter 的型別邊界上遺失的。

修正方式並非增加防禦性判斷，而是讓型別承載此語意：

```ts
/** null 的語意是「這個數字取不到」，不等於 0 */
export type Fundamental = number | null
```

- `parseFundamental` 對 `None`、`-`、缺鍵、`NaN` 一律回傳 `null`。
- 缺漏的指標**同時退出分子與分母**，分數在實際可評的權重上正規化。
- 可評權重低於 60 分時不發布評級，顯示 `NR`（Not Rated，沿用信評機構慣例）。
  在資料不完整的基礎上輸出「強力買進」，其風險高於不輸出。
- 介面明列哪些指標因缺資料未納入計分，分數的可信度因此是透明的。

手動輸入模式遵循同一規則：空欄位為 `null` 而非 0。表單的送出門檻直接引用
`CRITERION_WEIGHTS` 與 `MIN_RATABLE_WEIGHT`，避免出現「表單允許送出、結果卻是 NR」
的不一致。

### 2. 限流器在唯一需要它的情境下失效

重構前的節流邏輯為「讀取時間戳 → 間隔不足則等待 → 更新時間戳」。單一請求下運作正常，
但批次查詢以 `Promise.allSettled(symbols.map(...))` 同時發動，多個呼叫在同一個 tick
讀到**同一個** `lastRequestTime`，全部通過檢查後一起送出。

現行實作改為 promise 佇列，使請求確實排隊。測試將間隔調整為 40ms，直接驗證併發呼叫
之間的實際間隔（`client.test.ts`）。另一項細節是 `gate` 必須吞掉前一個任務的失敗，
否則單次請求失敗會使整條鏈進入 rejected 狀態，導致後續請求全部被連帶拒絕。

### 3. 價格的來源必須可追溯

為節省 API 配額，現價由 `P/E × EPS` 反推。此推算在數學上成立，但 P/E 與 EPS 均為
TTM 口徑，得到的是該份基本面快照對應的價格，可能落後市價數日至一季，用於計算
「52 週位置」時存在誤差。

因此價格不是裸 `number`，而是帶來源標記的型別：

```ts
export interface PriceQuote {
  value: number
  basis: 'quote' | 'derived'   // 即時報價 / 由 P/E × EPS 反推
}
```

介面因此無法在未標示來源的情況下將其顯示為「現價」。當價格不存在時，合理價區間仍可
計算（僅需 EPS 與帳面值），但溢折價為 `null`、verdict 為 `NO_PRICE`。缺少比價基準時，
任何「昂貴或便宜」的結論都不具依據。

### 4. 不對匿名數字掛上具名機構

`AnalystTargetPrice` 為不具名的綜合共識。重構前的說明文字寫為「高盛、摩根等機構預測
目標價 $X」，但 API 回應中不含任何機構歸屬資訊，於金融產品介面上屬於不實陳述。
現行文案一律使用「共識目標價」，並有一條測試斷言說明文字不含任何投資銀行名稱。

### 5. 測試以實效為目的，而非覆蓋率數字

重構期間，`presets.test.ts` 的「配置比例總和必須是 100%」條件偵測到一項既有的資料
錯誤：原本的「積極配置」加總為 **104%**，會導致使用者被要求投入超過本金的金額。

## 架構

```
src/
├── domain/          純函數領域層 —— 不依賴 React、不碰 I/O
│   ├── portfolioMetrics.ts   損益、配置佔比、核心衛星比重、再平衡偏離、目標進度
│   ├── buffett.ts            巴菲特評分、合理估價、買點訊號、價格來源解析
│   ├── advisor.ts            依「風險 × 年限」12 種組合產生配置與複利試算
│   └── presets.ts            五種預設配置模板
│
├── services/
│   ├── alphaVantage/         外部資料進入系統的唯一入口
│   │   ├── mapping.ts          純函數：欄位對應、單位換算、錯誤分類
│   │   ├── client.ts           I/O：fetch、節流佇列、快取
│   │   └── ttlCache.ts         帶存活時間的快取（時間來源可注入）
│   ├── portfolioRepository.ts  儲存介面（兩個實作都必須符合，編譯期把關）
│   ├── indexedDbRepository.ts  本地實作（離線可用，亦為雲端失敗時的退路）
│   ├── firestoreRepository.ts  雲端實作（動態載入，見〈效能〉）
│   └── storage.ts              後端選擇與退回策略
│
├── stores/          Zustand 全域狀態（非同步動作收在 store 內，狀態只有一份）
├── components/
│   ├── ui/          原子元件（Button／Card／StatTile／Badge…，以 CVA 管理變體）
│   └── charts/      資料視覺化（配置堆疊條 + 色票指派規則）
└── pages/           三大頁面：建立組合 / 投資組合 / 個股研究
```

**分層依據**：`domain/` 與 `services/` 的界線區隔「計算是否正確」與「資料存放於何處」
兩件事。更換儲存後端只需新增一個 `PortfolioRepository` 實作；調整評分規則只需變更
`domain/`，並由 `npm test` 即時驗證既有行為是否受影響。

`alphaVantage/` 內部再作一次切分：**純對應邏輯與 I/O 分離**。欄位名稱錯誤、單位換算
遺漏這類問題型別檢查無法攔截，只會使數值靜默失準，因此是最需要測試的部分。分離後
以固定的樣本 payload 即可測試，無須攔截網路。重構前此層無任何測試。

## 工程決策

**儲存後端以明確介面隔開。** 重構前 IndexedDB 與 Firestore 兩個實作僅是恰好具有同名
方法，彼此無型別關係，任一邊變更簽章 TypeScript 均不會提示。現行兩者皆
`implements PortfolioRepository`，不一致會在編譯期被攔下。雲端不可用時**自動退回本地**
而非中斷畫面，因為本應用在無雲端的情況下仍可完整運作。

**錯誤以分類而非訊息字串進行分支。** `AlphaVantageError` 帶有 `kind` 與
`recoverableByManualInput`。介面依旗標決定是否顯示「改用手動輸入」：配額用盡時應顯示，
標的為 ETF 時則不應顯示（手動輸入同樣無法分析 ETF）。以 `message.includes('ETF')` 判斷
會在文案調整後靜默失效。

**總額一律由持倉推導，不作增量加減。** 新增或移除持倉時若採「總額 ± 該筆金額」的作法，
只要有一條路徑漏算，誤差便會永久寫入資料。改為每次以 `calcPortfolioTotals(items)`
重算後，總額與持倉不可能不一致。

**除以零是由測試守住的邊界，而非防禦性程式碼。** 剛建立、尚未下單的組合投入金額為 0，
直接計算報酬率會得到 `NaN%` 並渲染至畫面。`gainPercent()` 對此情況回傳 0，且有對應測試。

**金額使用 `number` 是刻意的取捨。** 本專案是分析與顯示工具而非帳務系統，不具備科目
餘額、對帳，或金額累加後須與另一份紀錄完全相符的需求，浮點誤差落在顯示精度以下。
若延伸為需要記帳的系統，正確作法是改用最小貨幣單位的整數（分）或 decimal 型別，
並將幣別納入型別；此變更值得執行，但不應在無需求時預先付出複雜度。

## 設計系統

顏色在開發流程的**最後**階段決定，並以腳本驗證而非目視判斷。

- **單一 token 來源。** 所有顏色定義於 `index.css` 的 CSS 變數，透過 Tailwind 4 的
  `@theme inline` 讓 utility 直接引用變數。淺／深色僅需變更單一處變數，元件層無須撰寫
  任何 `dark:` 前綴。
- **類別色票依固定順序指派，不循環。** 順序本身即為色盲安全機制（相鄰色差最大化）。
  超過 8 個標的的部分折入「其他」（中性灰），而非產生第 9 個難以辨識的色相。
- **顏色依標的而定，不依排名而定。** 篩選掉某個標的時其餘不會換色，「VOO 是藍色」
  這項認知得以維持。
- **不以顏色作為唯一的表意通道。** 漲跌同時以箭頭方向與顏色兩個通道編碼；指標卡片具備
  「通過 / 未通過 / 無資料」三種狀態並各有獨立圖示，因為「未通過」與「無從判斷」
  對投資判斷的意義不同。
- **part-to-whole 採水平堆疊條而非圓餅圖。** 投資組合常有 8 至 9 檔持股，圓餅圖在超過
  6 個區段或數值相近時難以判讀。

配色在 `#ffffff`（淺）與 `#16181d`（深）兩個表面色上，各自通過色盲分離度、對比、
色度等六項檢查後才採用。

## 效能

Firebase SDK 被打入主 bundle，未設定雲端的使用者同樣需要下載。將環境判斷

## 測試策略

覆蓋率門檻**逐檔套用**（`perFile: true`），僅設於兩層：

- **`domain/`** —— 財務計算，錯誤會直接影響使用者的資金判斷。
- **`services/alphaVantage/`** —— 外部資料進入系統的唯一入口。此處的錯誤（欄位名稱、
  單位換算、缺漏值語意）型別檢查無法攔截，只會使數值靜默失準。

採逐檔門檻而非聚合平均的原因是：全域門檻會讓「All files 91%」掩蓋「`advisor.ts` 46%」，
使 README 宣稱的標準與實際不符，其問題大於覆蓋率偏低本身。改為逐檔後，該 46% 的成因
也隨之浮現：六個 `ETF_INFO[sym]?.name ?? sym` 形式的 fallback 永遠不會執行，因為 `sym`
全部來自寫死的配置表。將兩張表改為 `as const satisfies` 使 key 成為字面量聯集後，
查表即為完全的，fallback 得以直接刪除；往配置表加入未登錄的代碼會成為**編譯錯誤**，
而非在執行期靜默顯示裸代碼與空白理由。僅移除死程式碼一項，branch 覆蓋率即由 46%
提升至 86%。

為提高整體數字而測試 UI 樣式並無意義。測試以 `testFactories.ts` 提供合理預設值，
使每條測試僅需覆寫其真正驗證的欄位；驗證缺漏資料時明確寫入 `null`，讓「缺漏」在測試中
是刻意表達的意圖，而非遺漏填寫的結果。

涵蓋範圍包括：

- `advisor.ts` 全部 12 種「風險 × 年限」組合的配置正確性
- 巴菲特六項指標的權重與邊界，以及**缺資料與零分必須區分**的整組迴歸測試
  （缺負債資料不得取得滿分、缺流動比率不得遭到扣分、可評權重不足時不發布評級）
- 合理估價三種公式的數值正確性（對照獨立計算），以及無比價基準時不判斷貴賤
- adapter 層：`None`、缺鍵、`NaN` 一律轉為 `null`、比率換算百分比、API 錯誤分類
- client 層：併發節流、快取命中、失敗不寫入快取、單次失敗不影響後續請求
- 「除以零／空組合／超額達成」等邊界狀況，包含 `projectFV` 在年化 0% 時的除以零
  退化路徑。該分支無法經由公開 API 觸及，因此將函式匯出直接測試，而非保留一段
  未經驗證的防護。
